# Modern Wails by Release

## Summary

Wails v3 is the framework for new projects, and it replaces v2's single call and its context-bound bindings with an application object, windows, services and generated bindings. Write the v3 form, and when you port a v2 project, port it deliberately and keep v2 running until the v3 build works. Releases are weekly, and some 3.1 features are experimental, so pin the version and read each release's notes before you move.

## Rules

### Release timeline

| Release | Date | What it means for these notes |
| --- | --- | --- |
| v3 alphas | from January 2023 | The long pre-release period. Examples and blog posts from it show a different API, so ignore them. |
| v3 beta | 2026-08-02 | The beta announcement ("a new foundation for Go desktop applications"). |
| v3.0.0 | 2026-10-26 | Stable for desktop. Multiple windows, system tray, native menus and dialogs, services and generated bindings, the Taskfile build, the updater, packaging and signing guides, server builds, and experimental iOS and Android. Needs Go 1.26. |
| v3.1.0 | 2026-11-01 | The first weekly feature release. About 100 fixes, a stricter release rhythm, experimental CGo-free builds (`purego`) and the experimental Wake build configuration. The 3.0 documentation says that the legacy GTK3 stack is removed in 3.1, while the 3.1 post still lists GTK3 for the experimental Linux backend. |
| v3.2.0 | nightly | Dated pre-releases (`v3.2.0-nightly.20261103`). Do not use them for a product. |

- Wails ships weekly minor releases (`v3.1.0`, `v3.2.0`) and dated nightlies between them, after v3.0.0. Treat every minor release as a possible source of changes, and read its notes before you upgrade.
- The stable compatibility contract covers desktop: Windows, macOS and Linux on amd64 and arm64. Android and iOS are experimental and outside it.
- A change that the documentation calls experimental can change in any release. Do not adopt one without a written decision.

### Experimental features that this set does not use

- **CGo-free builds.** `WAILS_PUREGO=1 wails3 build`, or `CGO_ENABLED=0 go build -tags purego,production .`, builds macOS and Linux applications with no C compiler. CGo remains the default in 3.1, and the purego backends are marked experimental. Stay on the default, which is what the generated Taskfiles and the documentation's contract use.
- **Wake.** `WAILS_EXP_USE_WAKE=1` moves the build configuration into a `wails.yaml` and replaces the Taskfile routing, and the migration is one way. Stay on the Taskfiles, which you can read and edit and which the Go notes' automation fits ([build and distribution](10-build-and-distribution.md#building)).
- **Mobile.** The template includes `build/android` and `build/ios`. They are experimental, so do not ship them.
- Revisit this list when the documentation moves a feature out of experimental. A change of default needs a change in these notes first.

### Idioms to replace

Replace the old form in the lines you change.

| Wails v2 | Wails v3 |
| --- | --- |
| `wails.Run(&options.App{ ... })` with title, size and `Bind` together | `application.New(application.Options{ ... })`, then `app.Window.NewWithOptions(...)`, then `app.Run()` |
| `Bind: []interface{}{&App{}}` | `Services: []application.Service{application.NewService(value)}`, or `app.RegisterService(...)` |
| A struct with a `ctx context.Context` field set in `startup(ctx)` | A standalone service. Use `ServiceStartup(ctx, options)` when it needs setup, and a consumer-owned interface for what it needs from the application |
| `runtime.EventsEmit(ctx, name, data)` and `runtime.EventsOn(ctx, name, handler)` | `app.Event.Emit(name, data)` and `app.Event.On(name, func(event *application.CustomEvent) { ... })` |
| `runtime.WindowSetTitle(ctx, title)` and other context-bound runtime calls | Methods on the window object: `window.SetTitle(title)` |
| One window, implicit | Named windows from `app.Window`, found with `GetByName`, `Current` and `GetAll` |
| `wailsjs/go/main/App` imports | `frontend/bindings/<module>/...`, generated by `wails3 generate bindings` |
| `EnumBind` and manual enum registration | Automatic: a named type with constants becomes a TypeScript enum |
| Events as `...interface{}` | `application.RegisterEvent[T](name)` and a typed `Events.On` on the frontend |
| `wails.json` and the opaque build | `build/config.yml` and the Taskfiles |
| The `wails` CLI | The `wails3` CLI, pinned with a `tool` directive |
| `func init()` that registers an event | `application.RegisterEvent` at the start of `run` |
| `github.com/wailsapp/wails/v2` imports | `github.com/wailsapp/wails/v3/pkg/application` and friends |
| `@wailsapp/runtime` or the v2 injected runtime | `@wailsio/runtime`, pinned to the version of the Go module |

### Porting from Wails v2

- v3 is a new major version, and moving to it is a port and not a version bump. Wails v2 continues to receive critical updates, and its CLI (`wails`) and module path are separate, so both can be installed. Keep the v2 application working until the v3 one is ready.
- Port on a branch, in this order, and keep each step building:
  1. Create a v3 project with `wails3 init -t svelte`, and move your frontend and Go code into it, as the [layout note](03-project-layout.md#where-code-lives) describes.
  2. Convert the main struct into services. Remove the stored `ctx`, move setup into `ServiceStartup` and teardown into `ServiceShutdown`, and pass dependencies through constructors.
  3. Replace `runtime.*` calls with calls on the application and window objects, and register events.
  4. Regenerate the bindings, put a client module in front of them, and update the frontend imports.
  5. Replace `wails.json` settings with `build/config.yml`, and rebuild the icons and platform files.
  6. Bring the Go code and the frontend to these notes and the notes that they build on.
- Test the ported application on every platform that you ship. The webview and the window behaviour differ per platform, and the migration guide has a checklist.
- Do not mix v2 and v3 packages in one module.

### Upgrading within v3

- Pin one version in `go.mod`, in the `tool` directive's module (the same module) and in `@wailsio/runtime`, and change them together ([setup](02-project-setup-and-tooling.md#the-wails-cli)).
- Move one minor version at a time, in its own pull request. Read the release notes, run `go mod tidy`, regenerate the bindings, run the check task and the end-to-end test, and build every platform.
- `wails3 task common:update:build-assets` regenerates the platform files from `build/config.yml`. Run it after an upgrade only when you want the new platform files, and review the diff: it overwrites hand edits.
- Re-read this set when a release changes the default build, the bindings generator or the supported platforms.
- Read the installed version before you use an API: `go tool wails3 version`, or `go list -m github.com/wailsapp/wails/v3`. The documentation site shows the newest version, and the source of the version you installed is in the module cache.

[What's new](https://wails.io/whats-new/).
- Go module proxy on 2026-11-18: `github.com/wailsapp/wails/v3@latest` is `v3.1.0` (2026-11-01). GitHub releases list `v3.1.0` and the prereleases `v3.2.0-nightly.20261101` to `v3.2.0-nightly.20261103`.
- The old and new forms in the table come from the migration guide's examples and from the code that ran in the sample project: `application.New`, `app.Window.NewWithOptions`, `app.RegisterService`, `app.Event.Emit`, `application.RegisterEvent`, `wails3 generate bindings` and `@wailsio/runtime`.
