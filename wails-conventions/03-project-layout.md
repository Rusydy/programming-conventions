# Wails Project Layout

## Summary

A Wails project is a Go module with `main.go` at the root, domain and service code in `internal/`, the frontend in `frontend/` and the build files in `build/`. This is the "single command" layout of the Go notes, and the embed directive requires it. Commit the generated bindings, regenerate them whenever a bound type changes, and treat everything the CLI writes as generated.

## Rules

### Where code lives

- Keep `main.go` at the repository root, next to `frontend/`. The line `//go:embed all:frontend/dist` can only embed files below its own folder, so a `cmd/<name>/main.go` could not reach `frontend/dist`. The Go notes call this the "single command" layout: `main.go` and its files at the root, and the other packages in `internal/`.
- Put the domain code, and the services that expose it, in packages under `internal/`, named for what they provide (`loan`, `report`), not for their layer. This is the rule of the [Go notes](../golang-conventions/04-project-layout.md#rules-for-folders-and-packages). Do not create `services/`, `models/`, `repository/` or `controllers/` folders, which the Wails architecture guide shows.
- Keep `main.go` thin, as the Go notes say: `main` calls `run`, and `run` builds the logger, the services and the application, and passes dependencies down by hand ([application lifecycle](04-application-lifecycle.md#main-and-run)).
- Put a bound service in the package of the feature that it exposes, and keep it small. `internal/loan` holds the `Loan` type and `loan.Service`. The binding generator then writes `frontend/bindings/<module path>/internal/loan/`.
- Do not import `github.com/wailsapp/wails/v3/pkg/application` from a domain package. A service type may import it for `ServiceStartup`'s signature and nothing else, and the rest of the package stays free of it. Import `application` in `main` and in the adapters that `main` defines. A small interface owned by the consumer carries what the domain needs from the framework, such as publishing an event ([services and bindings](05-services-and-bindings.md#services)).
- Name a package after its responsibility and a type for what it is: `loan.Service`, not `loan.LoanService`. The generated frontend names the export `Service` too, so import it with an alias (`import { Service as LoanService } from ...`).
- Put files that the binary embeds (migrations, templates, seed data) in plainly named folders and embed them with `//go:embed`, as the Go notes say. The frontend embed stays in `main.go`.

```text
loansapp/
├── go.mod
├── main.go                 # thin: run builds and starts the application
├── Taskfile.yml            # build, run, package; plus the check task
├── build/                  # config.yml and the platform files, mostly generated
│   ├── config.yml          # product name, identifier, version, dev mode
│   ├── darwin/  windows/  linux/  ios/  android/  docker/
│   └── appicon.png
├── internal/
│   └── loan/               # domain types and the bound service
├── frontend/
│   ├── bindings/           # generated, committed
│   ├── dist/               # built frontend, embedded, ignored
│   ├── src/  public/  index.html
│   └── package.json  vite.config.ts  tsconfig*.json
└── bin/                    # build output, ignored
```

### Generated files

- `frontend/bindings/` is generated by `wails3 generate bindings -ts -i` (the template's task). Never edit it by hand. Every run with `-clean=true` deletes the folder first.
- Commit `frontend/bindings/`. The template does not ignore it, and the frontend checks (`svelte-check`, ESLint, the tests) need it to exist. Without it, a frontend developer or a CI job would need Go and the platform libraries just to type-check the Svelte code.
- Keep the committed bindings current. Add `wails3 generate bindings -clean=true -ts -i` followed by `git diff --exit-code frontend/bindings` to the check task ([setup](02-project-setup-and-tooling.md#scripts)), so a changed Go type with stale bindings fails the build.
- Regeneration is part of `wails3 build` and `wails3 dev`: the build task depends on the frontend task, which runs `generate:bindings` first. Run the command by hand after you change a bound type and before you run the frontend checks.
- Treat these as generated: `frontend/bindings/`, `frontend/dist/`, `bin/`, `.task/`, `.wails/`, and the platform files under `build/` that `wails3 task common:update:build-assets` rewrites from `build/config.yml`. Edit the source of a generated file (the Go code, `build/config.yml`), not the file.
- A generated file is exempt from the Go and TypeScript notes. Lint, format and type rules must not fail on it ([frontend](07-frontend.md#typescript-and-generated-code)).
- Do not move `frontend/bindings/`. The Vite plugin (`wails("./bindings")`) and the frontend import path (`@bindings/*` in the baseline) point at it. Change both together if you must.

### Build files

- Keep the `build/` folder in version control, except what `.gitignore` excludes. It holds the `Info.plist`, the Windows manifest and installer, the Linux packaging files and the icons that your release needs.
- Change the product information in `build/config.yml` (name, company, identifier, version, description, copyright) and run `wails3 task common:update:build-assets`. The command overwrites any edit that you made by hand to the files it generates.
- Replace `build/appicon.png` (and the `appicon.icon` folder for macOS) with your own icon before the first release. Run `wails3 task common:generate:icons` through the build, which does it for you.
- Do not delete the platform folders of platforms you do not ship. They cost nothing, and the build tasks include all of them. Remove `build/android` and `build/ios` only if you also remove their includes from `Taskfile.yml`.

### Existing projects

- A project that keeps `main.go` and domain code together at the root may stay so until a change moves a type into `internal/`. Move code when you touch it, one package per change.
- Keep a v2 project's layout until it is ported ([modern Wails by release](11-modern-wails-by-release.md#porting-from-wails-v2)).

## Sources and raw notes

Pages read on 2026-11-18, from the `v3.1.0` documentation source:

- [Project structure](https://wails.io/guides/dev/project-structure/): the files of a generated project, with `frontend/bindings/` as auto-generated Go bindings. [Architecture patterns](https://wails.io/guides/architecture/): the `services/` and `models/` folders and the repository pattern, which this note does not adopt. [Build system](https://wails.io/concepts/build-system/) and [build customisation](https://wails.io/guides/build/customization/): the Taskfile structure and `build/config.yml`.
- [Go notes](../golang-conventions/04-project-layout.md#choose-the-layout-by-project-type): the single command layout and the organise-by-responsibility rule.
- Checked on 2026-11-18 in the sample project: `wails3 init -t svelte` wrote `main.go` with `//go:embed all:frontend/dist`, `Taskfile.yml`, `build/` with `config.yml`, `darwin`, `windows`, `linux`, `ios`, `android` and `docker`, `frontend/` and `go.mod`, and its `.gitignore` held `.task`, `.wails`, `bin`, `frontend/dist` and `frontend/node_modules` and not `frontend/bindings`. After the service was moved to `internal/loan`, `wails3 generate bindings -clean=true -ts -i` reported `1 Service, 3 Methods, 1 Enum, 1 Model` and wrote `frontend/bindings/example.com/loansapp/internal/loan/{index,models,service}.ts`. The `build/Taskfile.yml` `build:frontend` task depends on `generate:bindings`.
- The advice to commit the bindings and to check them in the check task is this set's own choice. The documentation does not say whether to commit them. The reason for the embed rule is Go's `embed` behaviour, which does not allow `..` in a pattern.
