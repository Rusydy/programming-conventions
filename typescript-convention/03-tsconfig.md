# TypeScript tsconfig Conventions

## Summary

Start from the `tsconfig.json` that the framework generates, and add six options that catch real bugs at a low cost. Keep every other option off unless a note names it. New projects turn the six options on at once, and an existing project adopts them one option per change.

## Rules

### One tsconfig per environment

- A `tsconfig.json` describes one environment: its globals and its module behaviour. The TypeScript handbook gives this reason for one configuration file per environment.
- A Next.js application keeps the single `tsconfig.json` that `create-next-app` writes, because its server and client code share one program.
- Give a folder its own `tsconfig.json` only when its code runs in a different environment, for example `scripts/` that Node.js runs with `module: nodenext`. Exclude that folder from the root file. ESLint then finds the nearest file for each source file.

### Compiler options

| Option | Setting | Reason |
| --- | --- | --- |
| `strict` | `true` | The default since TypeScript 6.0. Keep it explicit so that TypeScript 5.9 projects behave the same. |
| `noUncheckedIndexedAccess` | `true` | Adds `undefined` to an index access, so `items[0]` is `Item \| undefined` and the code must handle an empty array. |
| `noImplicitOverride` | `true` | A subclass method needs the `override` keyword, so renaming a base method cannot detach an override unnoticed. |
| `noImplicitReturns` | `true` | A function returns a value on every path or on none. |
| `noFallthroughCasesInSwitch` | `true` | A `case` ends with `break`, `return` or `throw`. |
| `verbatimModuleSyntax` | `true` | Imports and exports stay as written, and a type-only import must say `type`. Bundlers and Node.js type stripping need exactly that. |
| `erasableSyntaxOnly` | `true` | Rejects `enum`, namespaces with code, parameter properties, `import =` and `export =`, so the code can run under type stripping. |
| `skipLibCheck` | `true` | The `create-next-app` default. It skips type checking of `.d.ts` files, which saves time and risks hiding a conflict between two copies of a library's types. |
| `isolatedModules` | `true` | The `create-next-app` default. Every file must compile on its own, as a transpiler such as SWC compiles it. |
| `module`, `moduleResolution` | `esnext` and `bundler` for a bundled app, `nodenext` for code that Node.js runs | The handbook's choice for each environment. |
| `target`, `lib` | The generated values in a Next.js app. `es2024` for Node.js 24 | SWC compiles a Next.js app, so the generated `target` stays. A Node.js project sets the ECMAScript version that its runtime supports. |
| `types` | Not set in a Next.js app. `["node"]` in a Node.js project | TypeScript 6.0 changed the default to `[]`. |
| `paths` | `{ "@/*": ["./*"] }` without `baseUrl` | The `create-next-app` alias. TypeScript 7.0 removed `baseUrl`. |
| `noEmit` | `true` | The bundler or Node.js runs the code, and `tsc` only checks it. |

### Baseline for a Next.js application

The block starts from the file that `create-next-app@16.4.3` writes and adds the six options. Apply the additions to a new project at once.

```jsonc
{
  "compilerOptions": {
    // generated by create-next-app
    "target": "ES2017",
    "lib": ["dom", "dom.iterable", "esnext"],
    "allowJs": true,
    "skipLibCheck": true,
    "strict": true,
    "noEmit": true,
    "esModuleInterop": true,
    "module": "esnext",
    "moduleResolution": "bundler",
    "resolveJsonModule": true,
    "isolatedModules": true,
    "jsx": "react-jsx",
    "incremental": true,
    "plugins": [{ "name": "next" }],
    "paths": { "@/*": ["./*"] },
    // added by these conventions
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true,
    "verbatimModuleSyntax": true,
    "erasableSyntaxOnly": true
  },
  "include": [
    "next-env.d.ts",
    "**/*.ts",
    "**/*.tsx",
    ".next/types/**/*.ts",
    ".next/dev/types/**/*.ts"
  ],
  "exclude": ["node_modules"]
}
```

- Keep the generated `include` and `plugins` entries ([Next.js TypeScript rules](../nextjs-convention/02-project-setup-and-tooling.md#typescript)).
- Do not add `types`. The generated `next-env.d.ts` loads the Next.js types, and those reference the Node.js types and declare `*.css`, `*.sass` and `*.scss` modules. A Next.js project therefore needs no `global.d.ts` for side-effect style imports, and TypeScript 6.0 does not change that.

### Baseline for a Node.js project

The block follows the settings that the Node.js documentation recommends for type stripping and the values of the `@tsconfig/node24` base, with one change: `allowImportingTsExtensions` replaces `rewriteRelativeImportExtensions`, because the project never emits JavaScript. Copy the values and skip the base package, because a few lines do not justify a dependency.

```jsonc
{
  "compilerOptions": {
    "target": "es2024",
    "lib": ["es2024", "ESNext.Array", "ESNext.Collection", "ESNext.Error", "ESNext.Iterator", "ESNext.Promise"],
    "module": "nodenext",
    "types": ["node"],
    "strict": true,
    "noEmit": true,
    "skipLibCheck": true,
    "verbatimModuleSyntax": true,
    "erasableSyntaxOnly": true,
    "allowImportingTsExtensions": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true
  },
  "include": ["**/*.ts"]
}
```

- `module: nodenext` implies `moduleResolution: nodenext`, `esModuleInterop` and `target: esnext`. Set `"type": "module"` in `package.json` so that `.ts` files are ES modules.
- Use the `lib` entries that match the runtime. The `ESNext.*` entries cover Node.js 24 (for example `Promise.try` and `Error.isError`). Remove the ones that the production runtime lacks.
- Imports name the file with its `.ts` extension, as Node.js requires ([modules and imports](06-modules-and-imports.md#imports)). `allowImportingTsExtensions` lets `tsc` accept that in relative and subpath imports, and it needs `noEmit`. A project that emits JavaScript uses `rewriteRelativeImportExtensions` instead, which rewrites relative imports only.

### Options that stay off

- `exactOptionalPropertyTypes`: it forbids writing `undefined` into an optional property, which clashes with many library types. In an existing project it adds errors, for little gain over the six options.
- `noPropertyAccessFromIndexSignature`: it forces `obj["key"]` on every index signature, so an existing project gets many errors from it.
- `noUnusedLocals` and `noUnusedParameters`: ESLint reports unused variables with `no-unused-vars`, so the compiler would report them twice.
- `@tsconfig/strictest`: it bundles the two options above and has 0.4 million weekly downloads, against 0.75 million for `@tsconfig/node24`. Write the options in the file instead of adding a base package.
- `checkJs`, `baseUrl`, `experimentalDecorators` and every option that TypeScript 6.0 deprecated ([modern TypeScript by release](12-modern-typescript-by-release.md#upgrading)).

### Adopting options in an existing project

- Turn on the options that report no errors first. `noImplicitOverride`, `noFallthroughCasesInSwitch` and `erasableSyntaxOnly` add no errors to a project that follows the baselines above.
- Then adopt one option per change, in this order: `noImplicitReturns`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`. Fix the errors in the same change, because TypeScript has no baseline mechanism.
- Every `verbatimModuleSyntax` error is TS1484, a type imported without `type`. The editor's quick fix that converts the import to a type-only import repairs them one by one.

### Changes in TypeScript 6.0 and 7.0

- TypeScript 6.0 and 7.0 change defaults: `strict` is `true`, `module` is `esnext`, `target` is the newest stable ECMAScript version, `noUncheckedSideEffectImports` is `true`, `types` is `[]` and `rootDir` is the folder of the `tsconfig.json`.
- TypeScript 6.0 deprecates `target: es5`, `moduleResolution: node10` and `classic`, `baseUrl`, `outFile`, `downlevelIteration`, `module: amd`, `umd`, `system` and `none`, and `esModuleInterop` and `alwaysStrict` set to `false`. Each one is an error until `"ignoreDeprecations": "6.0"` is set. TypeScript 7.0 rejects them all, and `ignoreDeprecations` no longer helps.
- With a `tsconfig.json` in the folder, `tsc file.ts` stops with TS5112 in both versions. Run `tsc -p .`, or pass `--ignoreConfig` to skip the file.
- The baselines above use none of the deprecated options, and a project that follows them needs no `ignoreDeprecations`. [Modern TypeScript by release](12-modern-typescript-by-release.md#upgrading) lists the upgrade steps.
